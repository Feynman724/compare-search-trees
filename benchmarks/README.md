# 2026-10-15 macOS 复现实验

使用用户提供的 `Peer Review/code/test.c` 及其引入的五个 C 实现，未修改算法或计时逻辑。在 Mac16,12（Apple Silicon，arm64）上用 Apple Clang 21.0.0、`-std=c11 -O2 -Wall -Wextra -Wpedantic` 编译。先执行 `--check`，五种树均通过；再执行完整 `--bench`。输入为 0 至 N−1，N = 1k、2k、5k、10k、20k、50k、100k；三种插入/删除顺序，各重复三次，五棵树共用每次试验的排列。计时使用程序内的 `CLOCK_MONOTONIC`，包括树操作中的分配和释放，不包括生成输入与写文件。没有绑定 CPU，也没有控制后台负载。

复现命令（在包含 `code/` 的提交目录执行；把输出目录改成自己的路径）：

```sh
clang -std=c11 -O2 -Wall -Wextra -Wpedantic code/test.c -o compare-trees
./compare-trees --check
mkdir -p inputs
./compare-trees --bench results.csv inputs
```

本次 `code/test.c` 的 SHA-256 为 `57d250b25eafb37408da01fc3cec7711871ec026799d67dcdcb13c1060ae15c0`。完整源代码由用户另行提供，未复制进网页仓库。

两组实验都显示：升序插入会使普通 BST 的总耗时远高于其他树；Splay 在这两种特定的有序序列中非常快。随机输入时，五种树的耗时回到同一数量级，两次测量的十万键排序均为 B+、BST、AVL、Splay、Red-Black。本机中 BST 对 B+ 的耗时差约 24.5%，原报告约 1.55%，因此“B+ 普遍最快”或“二者总是几乎一样快”都超出了证据。

本机随机组十万键的三次同种子配对中，BST 相对 B+ 的耗时差约为 48.4%、7.5%、19.3%；24.5% 是“各树三次总时间中位数”的比值差，并非精确的总体效应估计。这也说明只看一个小领先幅度并不稳妥。

两次测量的绝对毫秒值不能直接对比：原报告在 WSL2/Linux、Ryzen 7 H 255、GCC 13.3.0 `-O2` 上运行；本次在 macOS/Apple Silicon、Apple Clang `-O2` 上运行。仅三次重复且未控制后台负载，特别是接近的名次不应当作稳定的性能定论。
